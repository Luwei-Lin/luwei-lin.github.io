11:T16bc,<h1>Guardrails That Keep Vibe Coding From Going Sideways</h1>
<p>When I was working on a recent full-stack project, one thing I noticed pretty quickly was how easy it is for the frontend to get messy — especially when AI is helping you generate UI code. It's fast, it feels great, but without some kind of agreed-upon order of operations, you end up with a patchwork of random styles and one-off components that no one wants to touch later.</p>
<p>So here's the decision framework we landed on. It's not complicated, but having it written down made a real difference when reviewing PRs or using AI tools to scaffold UI.</p>
<hr>
<h2>The Order That Actually Matters</h2>
<p>When I'm implementing any piece of UI, I run through this order before writing a single line:</p>
<ol>
<li><strong>Check if the internal component library already has what I need.</strong> Our team's shared components are the first stop — reuse always wins.</li>
<li><strong>If not, reach for Ant Design directly.</strong> It covers most cases out of the box.</li>
<li><strong>Lean on Ant Design's built-in props before reaching for custom styles.</strong> Things like <code>size</code>, <code>variant</code>, <code>status</code>, layout primitives — these do more than people realize.</li>
<li><strong>If I need to tweak visuals, do it at the token level.</strong> Not hardcoded values.</li>
<li><strong>If it's truly custom UI</strong> (think floating nav, unique layout patterns), build it using tokens and existing primitives — not a soup of custom CSS.</li>
<li><strong>Any exception to the above? Talk to design first.</strong> Don't just go rogue.</li>
</ol>
<p>This order keeps things consistent and makes AI-generated code easier to review — if the output skips steps 1–3 and jumps straight to custom styles, that's a red flag worth catching.</p>
<hr>
<h2>What I Mean by "Token Level"</h2>
<p>This one trips people up, so it's worth spelling out.</p>
<p>Token-level means your visual values come from the theme, not from your head. Instead of <code>color: #1890ff</code>, you're using whatever the design system's primary token resolves to. In practice:</p>
<ul>
<li>App-wide overrides live in <code>ThemeConfig</code> — that's where token/component-level changes belong.</li>
<li>Inside component styles, use token-driven values. Hardcoded colors and font sizes should be rare.</li>
<li>Layout dimensions (widths, heights, padding) can be concrete values when there's no token equivalent — just check first.</li>
<li>When you do need custom styles, use <code>createStyles</code> from <code>antd-style</code>. This keeps styles tied to the active theme automatically.</li>
<li>Never reach for custom CSS when an Ant Design prop can do the same job.</li>
</ul>
<p>The point is that when the theme changes, everything should update together. Custom CSS that ignores tokens breaks that contract.</p>
<hr>
<h2>When the Default Order Doesn't Work</h2>
<p>Sometimes the design just doesn't fit neatly into the existing system. That's fine — but it means a conversation, not a workaround.</p>
<p>The usual outcomes when we hit this:</p>
<ul>
<li><strong>Update a token</strong> — if something needs to shift globally, do it at the source.</li>
<li><strong>Add a shared component</strong> — if it's reusable, it belongs in the library.</li>
<li><strong>Adjust the design</strong> — sometimes the right call is to meet the system where it is.</li>
</ul>
<p>Whichever path you take, log the decision in the PR. It keeps design and implementation in sync and makes future-you's life much easier.</p>
<hr>
<h2>How This Helps With AI-Generated UI</h2>
<p>The biggest risk with AI-generated frontend code is not that the first version is bad. It is that the first version is fast enough to feel acceptable, so the hidden inconsistency slips through review.</p>
<p>These guardrails give reviewers a simple way to evaluate the output:</p>
<table><thead><tr><th>Question</th><th>What to look for</th></tr></thead><tbody><tr><td>Did it reuse the internal component library first?</td><td>Existing shared components before new local components</td></tr><tr><td>Did it use Ant Design primitives before custom markup?</td><td><code>Button</code>, <code>Form</code>, <code>Table</code>, <code>Modal</code>, layout primitives</td></tr><tr><td>Did it use props before custom CSS?</td><td><code>size</code>, <code>status</code>, <code>variant</code>, <code>disabled</code>, layout props</td></tr><tr><td>Did custom styling come from tokens?</td><td>Theme-aware values instead of hardcoded colors</td></tr><tr><td>Did the PR explain exceptions?</td><td>Design sign-off or a short rationale</td></tr></tbody></table>
<p>This turns vibe coding from "the UI looks okay on my machine" into "the UI fits the system we already agreed to maintain."</p>
<hr>
<h2>Quick Review Checklist</h2>
<p>Before marking a UI PR ready for review, I run through this:</p>
<ul>
<li>[ ] Followed the component decision order</li>
<li>[ ] Used Ant Design primitives/props before writing custom styles</li>
<li>[ ] Visual customization goes through theme tokens where possible</li>
<li>[ ] Custom styles use <code>createStyles</code> from <code>antd-style</code></li>
<li>[ ] Custom components are token-driven</li>
<li>[ ] Any exceptions have a design sign-off and a rationale in the PR</li>
</ul>
<hr>
<h2>Takeaways</h2>
<ul>
<li>Vibe coding needs a decision order, not just taste.</li>
<li>Reuse internal components first, then Ant Design, then token-driven custom UI only when needed.</li>
<li>Tokens keep visual decisions connected to the design system.</li>
<li>AI-generated UI is easier to review when the anti-patterns are explicit.</li>
<li>Exceptions are fine, but they should be discussed and documented instead of quietly becoming precedent.</li>
</ul>
